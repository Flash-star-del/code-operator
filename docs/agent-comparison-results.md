## 方法（一段话）

三个冻结的合成 Python 任务（T1 区间合并 / T2 重试退避 / T3 事件分级），每个
系统-任务组合运行一次，严格串行、单元上限 360 秒、不重试。评分与被测系统完全
独立：全新 Git 工作区 + 隐藏测试（F2P/P2P）+ 文件范围检查；CLI 事件遥测不参与
评分。缓存产物（`__pycache__` 等）不计入变更。

排除决定本身在此公开声明，可供复核。

## code-operator 相对缺陷分析（基于全部留存运行的交叉证据）

以下缺陷从正式运行与各次 Pilot 的留存报告中交叉提取。Pilot 块按协议不是能力
结果，此处仅作为行为模式**可复现性**的辅助证据引用。

**D1 — 范围纪律不稳定（全部正式与扩展失败的直接原因）。** T1 的四次留存运行中，
三次残留自建临时验证脚本（尝试 3：`_verify_edge.py`+`_verify_edge_test.py`；
尝试 5：`_check_ranges_tmp.py`+`tests/_tmp_edge_check.py`；正式：
`_verify_ranges.py`），一次干净且最小（尝试 4：仅 `ranges.py` +1/−1，21.5 秒
resolved）；扩展 T4/T5 两单元再次全部残留（T4：`_verify_tmp.py`；T5：
`_verify_tmp.py`+`tests/test_extra_tmp.py`）。合计六次不同任务/运行中五次
残留，该模式已从"不稳定出现"上升为主导失败模式：倾向写"草稿验证脚本"
辅助推理，但缺少收尾清理步骤。值得注意的是 T4 的生产文件修复本身是 +1/−1
最小补丁——失败完全由残留脚本造成，而非补丁能力。Kimi Code 同期全部运行
零违规。改进方向：在循环收尾增加工作区自检/清理阶段，或在系统提示中约束
草稿文件生命周期。

**D2 — 退出码语义缺陷（本横评新发现的产品 bug）。** `resolved=True` 却返回
退出码 1 的组合出现两次（尝试 4 的 T1、正式的 T3），扩展 T4/T5 两单元亦均
以退出码 1 结束，而正式 T2 正常返回 0（`COMPLETED`）；观察到的七次运行中
六次以非零码退出。退出码不反映任务结果，会误导脚本化调用与 CI 集成。成因
待查（疑与收尾路径或轮次上限判定有关），应作为独立缺陷修复。Kimi Code
全部正常退出 0。

**D3 — 补丁不够最小。** 同一 T1 修复，Kimi Code 稳定 +1/−1；code-operator
除尝试 4 外为 +32～+49（含违规脚本行数）。T2 两系统都在允许范围内添加了回归
测试，code-operator 的补丁仍为 Kimi 的 4 倍（+44 vs +11）。T3 两者完全一致
（+14/−4）。倾向：过度生成辅助代码而非最小修复。

**D4 — 耗时更长且方差大。** T1/T3 上耗时约为 Kimi 的 2 倍（151–186.8s vs
65.5–91.6s；122.4s vs 62.2s），扩展 T4/T5 上约 2.3 倍（157.0s/155.9s vs
56.2s/82.8s），且跨运行方差大（T1 从 21.5s 到 186.8s）；但 T2 上反而更快
（92.0s vs 102.9s），并非全面劣势。

平衡起见：code-operator 通过的任务全部隐藏测试满分，T3 与 Kimi 的解完全同构，
扩展 T4 的生产修复与 Kimi 逐行等价（+1/−1），失败集中于工程习惯（D1）而非
补丁能力；D1、D2 在扩展运行中均再次复现，可直接转化为后续修复项。

## 局限与后续工作

单次运行、五个合成任务（三个预注册 + 两个同日扩展），不构成统计结论，不计算
显著性或置信区间，不可与官方 SWE-bench 比较。科研级版本需要：每组合多副本、
更大且更多样的任务集、故障系统的根因隔离与重测、以及跨运行窗口的重复。
