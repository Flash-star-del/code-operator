# E2 黄金 Eval 设计规格

- 状态：项目作者已于 2026-08-29 批准完整设计
- 适用范围：`evals/golden_bug/`、`evals/run_golden.py`、对应离线测试、README 与脱敏运行证据
- 模型：通过现有环境变量配置的 `kimi-k3`

## 目标与非目标

目标是建立一个可重复、难度适中且适合两分钟录像的 Python 修复任务。它必须迫使 Agent 读取并追踪两个生产文件之间的数据流，独立运行初始失败测试，修改一至两个生产文件并复测。三次正式运行使用完全相同的冻结项目、任务提示、模型配置和成功判据，每次都在全新临时工作区执行；至少成功两次才可作为视频候选。

本阶段不修改 AgentLoop、工具、安全策略或上下文管理，不增加 Agent SDK/框架，不实现 E3 的终端轨迹，也不宣称三次样本代表整体成功率。如果正式运行暴露可复现的核心缺陷，必须另开 TDD 修复范围；修复后废弃旧计数并从三次全新运行重新开始。

## 冻结项目

目录结构：

```text
evals/golden_bug/
  task.txt
  project/
    .gitignore
    pricing.py
    invoice.py
    tests/
      test_invoice.py
```

`.gitignore` 仅忽略 `.code-operator/`、`.pytest_cache/`、`__pycache__/` 和 `*.pyc` 等运行产物。项目不依赖网络、随机数、当前时间或第三方运行库。

业务统一使用非负整数“分”，不使用浮点数：

1. 每行小计为 `unit_price_cents * quantity`。
2. 折扣金额为 `subtotal_cents * discount_percent / 100` 的正数四舍五入结果。
3. 折后小计为小计减折扣金额。
4. 税费以折后小计为基数，同样按正数四舍五入计算。
5. 最终金额为折后小计加税费。

`pricing.py` 负责行小计、正数比例四舍五入和折后小计。冻结缺陷是折扣金额使用向下取整。`invoice.py` 定义订单输入与汇总结果并调用 pricing；冻结缺陷是税费错误地使用折扣前小计作为基数。测试使用常量期望覆盖无折扣基线、折扣半分边界、折后计税和多商品合计，使初始项目部分通过、部分失败，修复两个根因后全部通过。

`task.txt` 是冻结提示，要求先检查代码并运行测试、不得修改测试文件、修复根因后再次运行测试并依据真实结果总结。它不泄露具体缺陷或参考实现。

## 运行器与数据流

`evals/run_golden.py` 复用现有 `load_provider_config()` 和 `run_task()`，不复制 Agent 核心。命令行必须显式提供 `--report <path>`；报告使用排他创建，目标已存在时退出且不覆盖。正式入口固定执行三次，不提供把单次调试结果冒充正式统计的选项。

每次运行的顺序如下：

1. 创建全新临时目录，只复制 `project/` 内容。
2. 计算冻结项目树哈希、提示哈希和全部测试文件组合哈希。
3. 在临时目录执行 `git init` 与 `git add --all`，建立只用于最终 diff 的索引基线；不提交、不推送，也不改变真实仓库。这是 Eval harness 行为，不是 Agent 的影子 Git 功能。
4. 使用 `sys.executable -m pytest -q`、参数数组、`shell=False`、固定 cwd 和 60 秒超时执行独立前置测试。前置测试若为零，整个正式批次判为 `INVALID_FIXTURE`，且不得调用模型。
5. 调用 `run_task()`，显式设置 `auto_approve_tests=True`，审批回调对其他 ASK 命令返回拒绝。该模式只信任冻结测试项目，不构成 OS 沙箱。
6. 无论 Agent 是否成功结束，都在可行时独立复跑 pytest，并重新计算测试哈希。
7. 读取 `git diff --binary --`、`git diff --name-only --` 和 `git status --porcelain --untracked-files=all`，记录变更与意外新文件。
8. 将该次结构化结果加入内存；临时目录退出时清理。失败运行同样保留在最终报告中。

三个工作区、提示、fixture 哈希、模型名和数值限制必须一致。某次模型或测试异常只使该次失败并记录稳定原因，不得静默丢弃；fixture 前置条件失效则停止整个批次，因为后续结果没有意义。

## 成功判据

单次运行只有同时满足以下条件才算成功：

1. 初始 pytest 退出码非零。
2. Agent 停止状态为 `COMPLETED`。
3. 最终 pytest 退出码为零。
4. 所有测试文件的组合 SHA-256 与运行前完全相同。
5. 已跟踪变更路径只属于 `pricing.py`、`invoice.py`，且没有非忽略的意外新文件。
6. 最终 Git diff 非空。

测试通过但修改测试、Agent 宣称完成但独立测试失败、没有生产代码 diff、修改额外文件或 usage 缺失都不得被掩盖。usage 缺失本身不否定代码修复成功，但报告必须保存 `null` 并标记不完整，不能伪造真实 token。

正式批次固定三次。报告计算 `success_count`；只有 `success_count >= 2` 才设置 `video_candidate=true`，README 只能表述为“该固定任务三次中成功两次/三次”。若少于两次，先定位 Agent 根因，不换成更简单题；任何修复完成后重新进行完整三次计数。

## 报告契约与隐私

报告使用版本化 JSON，顶层包含：

- `schema_version`、平台与 Python 版本；
- 模型名及轮次、工具调用、上下文和输出限制，不含 API Key；
- fixture 树哈希与冻结提示哈希；
- `run_count`、`success_count`、`video_candidate`；
- 三个按顺序保存的运行结果。

每次结果包含：序号、成功布尔值、稳定失败原因、初始/最终测试退出码与简短摘要、Agent 停止原因、模型轮次、工具调用数、供应商真实总 token 或 `null`、usage 是否完整、测试哈希是否变化、变更路径和完整 Git diff。

报告不得保存 API Key、Authorization、请求 ID、供应商响应正文、reasoning、完整消息历史、工具原始参数/输出或临时工作区副本。pytest 只保留稳定摘要；代码变化由 Git diff 表达。写入前使用现有 `Redactor` 对报告对象递归脱敏，并以 UTF-8 JSON 排他创建。

## 错误处理

- 报告路径无效或已存在：在任何模型调用前失败。
- Git、复制或前置测试基础设施失败：停止批次并返回非零，不生成看似完整的正式统计。
- 初始测试通过：记录/报告 `INVALID_FIXTURE`，不得调用模型。
- 单次模型失败、终止状态非成功、后置测试失败、测试哈希变化或越界文件变化：记录为该次失败，继续下一个全新工作区。
- pytest 或 Git 命令超时：终止对应子进程，记录稳定错误；不得把超时当测试失败通过成功判据。
- 三次完成后无论是否达到 2/3 都写入报告；进程仅在达到视频候选门槛时返回零。

## 测试策略

所有实现遵循红—绿—重构：

1. 冻结 fixture 测试先证明初始项目失败，并用测试期望锁定正确业务规则。
2. 运行器单元测试覆盖新临时目录、fixture 已通过时禁止模型调用、成功修复、`COMPLETED` 但后测失败、测试文件被修改、意外路径、空 diff、usage 缺失、超时/基础设施错误和报告拒绝覆盖。
3. 运行器集成测试注入脚本化假模型，通过真实 `run_task()`、文件工具和 pytest 完成离线闭环；测试进程继续禁止未模拟网络。
4. JSON 安全测试以合成秘密验证递归脱敏，并断言禁止字段不存在。
5. 全量离线测试和 Windows/Python 3.11 CI 保持阻塞；CI 不读取真实 Provider 环境变量，也不调用 Moonshot API。
6. 实现审核通过后才运行真实三次 Eval；实际脱敏报告、前后测试和 diff 进入 E2 人工审核范围。

## 文档与交付边界

README 增加正式运行命令、冻结条件、2/3 判据、测试自动审批边界和实际结果链接。DESIGN/DEFENSE 只在真实三次运行后补充已验证事实。失败运行不能删除或改写；报告必须与提交中的 fixture、提示和模型配置哈希一致。

E2 结束条件是离线实现测试通过、真实三次结果已保存并如实解释、人工审核完成、提交 `test(eval): add reproducible golden coding task`，再单独通过第 9.5 节推送门禁。E3 终端轨迹、最终录像、姓名 ZIP 和延期的模拟答辩仍保持后续未完成。
