# 三系统横评限时收敛设计

**状态：** 已获项目作者原则批准（2026-09-02）；等待书面设计人工审核

**目的：** 在时间受限的前提下，将 code-operator、Claude Code 与 Kimi Code 的正式 Track A 从两次重复的 18 单元压缩为一次重复的 9 单元描述性微基准，同时修正已被真实 Pilot 暴露的评测基础设施缺陷，保留三个系统、三个冻结任务和统一隐藏评分的完整覆盖。

## 1. 修订依据与研究口径

原设计为 `3 个系统 × 3 个任务 × 2 次重复 = 18` 个正式单元。项目作者在任何正式 Track A 单元运行前明确接受取消重复性研究，将正式样本缩减为 `3 × 3 × 1 = 9`。本修订属于运行前的透明设计变更，不把单次观测描述为稳定成功率，也不计算显著性、置信区间或行业排名。

三个已执行的 T1 Pilot 均因评测基础设施问题排除，不进入正式分子或分母：第一次在 Windows 只读 Git 对象清理处中止，第二次由过窄 OS 环境导致三个产品无法正常启动，第三次暴露 Git 状态缓存误判与真实 CLI 事件格式不匹配。原始无效证据必须保留，不能覆盖、删除或重新解释为产品能力结果。

本修订不改变以下冻结边界：三个必测产品、统一 `kimi-k3` 模型声明、T1/T2/T3 fixture 和 prompt、每单元全新工作区、360 秒共同超时、隐藏测试、允许修改范围、串行执行、失败保留、禁止自动重试和本地非保留原始供应商输出。任何正式运行仍需重新展示完整外发范围并取得单独授权。

## 2. 样本设计与执行顺序

正式 Track A 包含且仅包含九个唯一 `(system_id, task_id, replicate=1)` 单元，每个系统在 T1、T2、T3 上各运行一次，每个任务块恰好包含三个系统。顺序由冻结种子重新生成并写入新 manifest；同一输入两次生成必须得到字节相同的规范 JSON。生成后向项目作者展示实际九单元顺序、系统配置、任务哈希和 manifest 哈希。

执行保持严格串行。并行会使三个产品竞争同一 Moonshot 服务、本机 CPU、磁盘和进程资源，引入无法从九个小样本中分离的限流与资源混杂，因此不作为限时加速手段。每单元最多 360 秒；超时、拒绝、非零退出、错误补丁或低分都作为该单元结果保留，不重跑。最坏正式运行时间为 54 分钟，按已观察 T1 用时预计约 20–35 分钟。

Pilot 仍是正式运行的前置基础设施门禁。基础设施修复完成并通过离线测试后，必须用新 manifest 运行一次完整三系统 T1 Pilot；三单元均完成独立工作区创建、产品退出、隐藏评分、报告写入和清理，且没有评测器级失败，才允许申请正式 Track A 授权。Pilot 的补丁质量不进入正式统计。

## 3. 主判据与辅助遥测

产品能力的主判据只由产品退出后的独立 grader 给出，grader 统一检查：冻结基线、普通参与者文件变化、允许修改范围、隐藏 fail-to-pass、冻结 pass-to-pass、语法与回归、补丁哈希及任务特定要求。正式结论以这套隐藏评分和实际补丁为准。

Python 与 pytest 运行产生的 `__pycache__`、`.pytest_cache` 和 `*.pyc` 是评测过程噪声，不是参与者补丁。过滤必须在所有变化来源的统一入口生效，包括 Git 状态、独立工作区枚举、补丁哈希、行数与范围判断；不能只过滤其中一条路径。其他未授权文件仍按原规则判为范围违规，不能借缓存修复放宽。

Kimi Code、Claude Code 和 code-operator 的机器可读事件继续作为辅助遥测，用于尽力观察产品内是否调用测试以及供应商是否提供 usage。事件解析成功时记录允许的布尔值或计数；格式未知、字段缺失或解析失败时记录 `tests_observed=false`、`usage="unavailable"` 和对应遥测状态，但不得覆盖已经成功完成的独立隐藏评分。不得因追逐供应商私有事件格式而增加宽松的任意 JSON 猜测，也不得保存原始 stdout、stderr、最终回答、reasoning 或工具 payload。

进程超时、工作区创建失败、grader 无法运行、基线不一致、报告无法排他写入或清理失败仍属于评测基础设施错误，必须使 Pilot 失败关闭。产品自身非零退出或错误补丁属于产品结果，不得误分为基础设施错误。

## 4. Manifest 与证据版本

样本数和 Pilot 判定语义均已改变，因此必须生成新 schema/protocol 版本的 manifest，并使旧 manifest 及其三个无效 Pilot 报告保持原字节和原哈希。新 manifest 继续显式记录：研究标识、schema 版本、固定种子、三个系统配置、T1/T2/T3 精确哈希、九个正式单元、三个 Pilot 单元、360 秒超时和 Track B 状态。

新报告每行必须携带新 manifest 哈希、任务哈希、顺序号、系统、任务、固定 `replicate=1`、脱敏 adapter 状态、grader 结果和补丁哈希。正式报告要求恰好九个唯一单元，不允许缺失、重复、未知系统、未知任务或其他 replicate。汇总只报告每个系统实际 `x/3`、逐任务结果和九个原始单元；不将 Pilot 并入统计，不把单次成功率推广为产品总体能力。

若 Pilot 后再次修改 grader、fixture、prompt、系统命令、环境边界、超时、主判据或报告 schema，该 Pilot 与新 manifest 一并失效，必须停止并重新审核。若仅供应商事件遥测不可用而独立 grader、隔离、报告和清理均有效，则如实保留 unavailable，不再为遥测追加调试轮次。

## 5. TDD 与验证门禁

实施必须保持红—绿—回归顺序：

1. 先写一个真实 Git 工作区失败测试，使缓存通过 `git status` 出现，并证明当前 grader 错误报告范围违规；确认 RED 后才在统一变化入口做最小过滤。
2. 先写 Kimi/Claude 退出码为零、事件格式未知但隐藏 grader 可完成的失败测试；确认 RED 后只分离“能力主判据”和“辅助遥测状态”，不扩张解析器。
3. 将 manifest 测试从 18 个正式单元改为九个，直接覆盖三个系统、三个任务、唯一 `replicate=1`、固定种子顺序、缺失/重复/未知值拒绝和规范字节稳定性。
4. 运行横评专项测试、完整离线测试、编译检查、差异格式检查、凭据与临时文件扫描；任何失败都不得进入真实 Pilot。
5. 人工复核实现、测试和新 manifest。真实 Pilot 前重新展示 T1 完整合成数据范围并取得仅覆盖三单元的新授权。
6. Pilot 有效后，重新展示 T1/T2/T3 全部外发范围和九单元顺序，取得仅覆盖九个正式单元的新授权。Pilot 授权不得继承为正式授权。
7. 正式运行后不修改原始报告；完成统计、限制说明、项目作者人工审核、本地语义化提交和 v4.5 第 9.5 节独立推送门禁。

## 6. 失败处置与时间止损

- **本地测试失败：** 不运行外部产品；先定位根因并以最小 TDD 修复。
- **Pilot 基础设施失败：** 保留完整平衡块为无效证据，不进入正式 Track A；不得选择性复用成功单元。
- **Pilot 产品行为失败：** 只要工作区、进程、grader、报告和清理有效，就不因低分或非零退出重跑。
- **正式产品失败：** 作为九单元之一保留，不重试、不替换、不修改 prompt。
- **外部服务或授权边界阻塞：** 停止后续单元，如实报告已完成与未完成，不伪造完整九单元汇总。
- **安全异常：** 怀疑凭据或未授权数据外泄时立即停止，不以赶时间为由继续。

限时目标为：本地修订与全量验证 25–35 分钟，新 Pilot 6–12 分钟，正式九单元 20–54 分钟，统计与交付检查约 20–30 分钟。删除重复次数是唯一改变证据强度的加速措施；不通过降低隐藏测试、选择简单任务、缩短成功判据、并发制造混杂或删除失败样本换取速度。

## 7. 有效性威胁

- 每个系统—任务组合只有一个样本，无法估计模型随机性或复现稳定性。
- 三个任务均为小型冻结 Python fixture，结果只适用于当前版本、当前配置和当前时间，不能代表真实大型仓库或官方 SWE-bench。
- 三个产品虽然声明统一 `kimi-k3`，仍具有不同 scaffold、prompt 包装、工具、安全策略和上下文管理；比较单位是完整产品，不是孤立基础模型。
- 辅助事件遥测不可用会减少过程解释力，但独立隐藏评分仍能回答补丁是否满足冻结任务；二者必须分栏报告。
- 在观察三个无效 Pilot 后修订 evaluator 会产生后验设计风险，因此旧证据、修订时间和修订理由必须完整披露，正式样本不得反向影响主判据。
